Résumé du cours

L'affichage des messages d'erreur de manière ergonomique est essentiel. Il faut éviter de harceler l'utilisateur avec des alertes rouges dès l'affichage du formulaire, et n'afficher les erreurs que s'il a interagi avec le champ.

1. Conditions d'affichage

Pour n'afficher les erreurs que lorsque l'utilisateur a cliqué ou écrit dans un champ, on vérifie l'état d'interaction avec les flags touched ou dirty : 

          HTML (v17 - ngIf)
          <div *ngIf="control?.invalid && (control?.dirty || control?.touched)">
            // Afficher l'erreur ici
          </div>
        
          HTML (v18-v20 - @if)
          @if (control?.invalid && (control?.dirty || control?.touched)) {
            // Afficher l'erreur ici
          }
        
          HTML (v21 - Signals @if)
          @if (control?.invalidSignal() && (control?.dirtySignal() || control?.touchedSignal())) {
            // Afficher l'erreur ici
          }

2. Cibler une erreur précise : `hasError()`

La méthode hasError(name) permet de vérifier quel validateur a échoué afin d'afficher le message adapté : 

        HTML
        <p *ngIf="form.get('username')?.hasError('required')">Ce champ est obligatoire.</p>
        <p *ngIf="form.get('username')?.hasError('minlength')">Trop court ! (minimum 4 caractères).</p>

Formulaire

Entrez un nom d'utilisateur. Sortez du champ (blur) ou tapez moins de 4 caractères pour déclencher les alertes.

⚠️ Le nom d'utilisateur est requis.

⚠️ Le nom d'utilisateur doit faire au moins 4 caractères (actuellement : {{ form.get('username')?.value?.length || 0 }}).

Conclusion

touched & dirty :
`touched` passe à vrai dès que le champ perd le focus. `dirty` passe à vrai dès que sa valeur change. Combiner ces deux états évite d'afficher des erreurs avant toute interaction.
hasError('validator') :
Indispensable pour offrir une expérience utilisateur claire en distinguant un champ vide d'un format erroné.
